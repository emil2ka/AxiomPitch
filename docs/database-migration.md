# Профили и подготовка к Supabase

Текущая база — SQLite на этом компьютере. Профиль имеет стабильный UUID, презентации и результаты — `profile_id` с внешним ключом. Настройки и последний открытый документ хранятся у профиля. Браузер остаётся офлайн-кэшем: мост не нужен для просмотра локальной презентации. Выход не удаляет данные.

## Подключение Supabase

Код аккаунтов уже в проекте (`src/lib/cloud.ts`) и включается двумя переменными.

1. Создай проект на [supabase.com](https://supabase.com/dashboard). В **SQL Editor** выполни целиком `database/postgres-schema.sql` один раз.
2. **Authentication → URL Configuration**: Site URL — адрес сайта (для разработки `http://localhost:5173`); в Redirect URLs добавь `http://localhost:5173/**` и боевой адрес с `/**`. Иначе ссылки из писем не вернут на `/login` и `/reset-password`.
3. **Project Settings → API**: скопируй Project URL и publishable key (или anon key) в `.env.local`:
   `VITE_SUPABASE_URL=https://xxxx.supabase.co` и `VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_…`. Ключ `service_role`/secret во фронт не класть никогда.
4. Письма: встроенный отправитель Supabase пишет только участникам команды проекта и несколько писем в час. Для настоящих пользователей подключи SMTP (**Authentication → Emails → SMTP Settings**). Для быстрой проверки можно выключить **Confirm email** в Authentication → Sign In / Providers → Email.
5. Перезапусти `npm run dev`, открой `/register`.

Что синхронизируется: имя, дата обучения, настройки чёлки/чувствительности/длительности/прогресса обучения (`profiles.preferences`) и итоги репетиций (`sessions`). Номер экрана чёлки и PDF остаются на устройстве. Профиль создаётся при первом входе с `id` = ID пользователя Auth. Прежние локальные профили на этом устройстве не присоединяются к аккаунту автоматически: владельца определяет перенос ниже. Выход из аккаунта завершает сессию только в этом браузере.

## Локальные профили

Это локальные профили, не аутентификация. Заголовок `X-Axiom-Profile` задаёт область данных, но не доказывает личность. HTTP-сервер слушает только loopback. Перенос этого заголовка в публичный API недопустим: облачная версия должна использовать Auth и RLS.

## Контракт

`PUT /api/profiles/:id` создаёт/обновляет профиль; GET возвращает настройки, рабочее пространство и статистику. PATCH `preferences` сохраняет настройки. PUT `workspace` хранит ссылку на принадлежащий профилю PDF, имя и позицию. PDF и результаты используют отдельные таблицы; их API фильтрует по профилю, включая чтение PDF и запись заметок. Без профиля доступны только старые непривязанные записи, а не все пользователи. POST `migrate` однократно привязывает только ссылки из существующего браузерного профиля, не переписывая чужого владельца.

## Перенос

1. `npm run db:export -- /полный/путь/snapshot.json` создаёт согласованный JSON-снимок. Скопировать отдельно папку `server/data/presentations`; файл manifest указывает имена PDF. Экспорт включает непривязанные старые данные, чтобы ничего не потерять.
2. Для Supabase подготовлена `database/postgres-schema.sql`: UUID, внешние ключи, `timestamptz`, `jsonb`, индексы и RLS. Скрипт ещё не применён к облаку и требует проверки на целевом PostgreSQL.
3. Создать пользователей через Supabase Auth и составить явную карту `local_profile_id → owner_user_id`. UUID профиля сохраняется, если он валиден; единственный старый ID `legacy` нужно заменить UUID вместе со всеми ссылками. Непривязанные записи не импортировать автоматически под первого пользователя — сначала определить владельца.
4. Импортировать profiles, затем presentations, затем sessions. В presentations поле `file` заменить на `storage_key`, например `profile_id/presentation_id.pdf`. JSON preferences/workspace/result переносится без изменения смысла; даты становятся timestamptz.
5. PDF загрузить в приватный Storage bucket; добавить политики владельца и выдавать временные ссылки вместо локальных URL. Видеопоток никогда не выгружается.
6. Заменить реализацию HTTP-репозитория и добавить Auth. Локальный Mac-мост для управления Keynote и чёлки остаётся на компьютере. Не переносить его команды в публичный сервер.
7. Проверить запросы двух разных Auth-пользователей и анонимного клиента: чужие профили, PDF и результаты должны быть недоступны. В текущем проекте тестируются локальная принадлежность, изоляция, миграция и сохранение данных при повторном открытии SQLite.

Схема учитывает официальные рекомендации [Supabase о таблицах](https://supabase.com/docs/guides/database/tables), [данных пользователя](https://supabase.com/docs/guides/auth/managing-user-data) и [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). Сервисные ключи и Supabase-проект пока не нужны.
